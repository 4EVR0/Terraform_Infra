# Terraform 마이그레이션 작업 계획

## 성공 기준

- 프로젝트 AWS 자원과 코드의 연결 관계 추적 가능
- 첫 편입에서 자원 생성·수정·삭제·교체 없음
- 편입 이후 `terraform plan`에서 관리 대상 자원에 대한 변경 없음 확인
- 팀원이 동일한 상태 파일과 잠금 체계를 사용해 중복 변경 방지
- 테스트 환경에서 인프라 재구성과 데이터 복원 절차 검증

`import`는 기존 자원을 Terraform의 관리 목록인 **state**에 연결하는 작업. 서버를 새로 만들거나 애플리케이션을 배포하는 작업과 구분.

## 1. 자원 목록과 관리 범위 확정

- [x] 서울의 주요 자원·S3·EC2 연결 IAM 조회
- [x] 전체 프로젝트 AWS를 목표 범위로 설정
- [x] 활성 리전 전체의 지원 서비스 조회 및 누락 범위 기록
- [ ] 기본 VPC·서브넷·공유 SSH 그룹의 소유 범위 확인
- [x] EC2·CI 관련 IAM 정책 본문, S3 추가 설정, ECR 정책, Glue 테이블 목록 조회
- [ ] 나머지 IAM 주체와 Glue 등 자동 생성 자원의 소유 범위 확정
- [ ] 백업·스냅샷·배포 자동화와 연결된 AWS 자원 확인

**산출물:** 자원별 AWS ID → Terraform 주소 → 소유자 → 상태 파일 대응표.

실제 조사 결과와 관리 범위 제안은 로컬 상세 기록에 보관. 프로젝트 전용 후보와 공유·소유 불명 자원 구분은 완료했으나, 팀 소유 확인과 구체적인 Terraform 주소 확정은 남아 있음.

## 2. 팀 공용 상태 저장소 준비

- 기존 데이터 버킷과 분리된 전용 S3 버킷 사용
- 버전 관리·암호화·공개 접근 차단·상태 잠금 활성화
- S3 기본 잠금 기능 `use_lockfile = true` 사용 제안
- 초기 단계는 SSE-S3 제안. 별도 키 접근 통제가 필요하면 SSE-KMS 검토
- 상태 파일 읽기·쓰기와 잠금 파일 생성·삭제에 필요한 팀 권한 설계
- 버킷 부트스트랩 구성을 애플리케이션 자원 구성과 분리하고, 부트스트랩 상태 보관 위치도 기록
- 버킷 이름·실행 역할·팀원 접근 방식 확정 후 실제 생성

**완료 기준:** 두 실행자가 같은 상태에 동시에 변경을 시도할 때 잠금 동작 확인, 이전 상태 버전 복원 절차 문서화.

상태에는 민감한 값이 포함될 수 있으므로 Git에 저장하지 않음. 잠금은 동시 실행 충돌 방지 기능이며 백업 대체 수단이 아님.

## 3. 첫 편입 — 모니터링 EC2 한 대

선정 이유: 프로젝트 공용 모니터링이라는 역할이 명확하고, 단일 EC2로 import 절차 검증 가능. 모니터링 데이터가 있으므로 임의 재생성 불가.

1. 최신 상태 재조회: AMI·유형·서브넷·보안 그룹·IAM 프로파일·루트 디스크·태그
2. 기존 보안 그룹·프로파일은 우선 이름/ID로 참조
3. `imports.tf`의 모니터링 대상 import 블록과 실제 ID 확인
4. `terraform plan -generate-config-out=generated.tf`로 현재 속성에 기반한 코드 초안 생성
5. 생성된 코드의 불필요한 계산값·충돌 속성·민감값 검토, `prevent_destroy` 적용 검토
6. 저장할 plan에서 `1 to import, 0 to add, 0 to change, 0 to destroy` 확인
7. 코드·대상 계정·원격 state 경로를 함께 검토한 뒤 해당 plan 적용
8. 다시 plan 실행하여 자원 변경 없음 확인, 중지 상태·디스크 연결 유지 확인

생성된 코드는 초안이므로 그대로 적용하지 않음. `prevent_destroy`도 구성 자체를 제거하는 실수나 콘솔 변경까지 막아주지는 않음.

사용자가 PR 머지 후 새 plan을 적용하고 후속 `No changes`를 확인하여 첫 편입 완료. 실행 결과는 사용자 확인으로 기록하며, 서버 애플리케이션 상태 검증과는 구분.

## 4. 나머지 자원 편입

| 순서 | 자원 | 핵심 확인 사항 |
|---|---|---|
| 0 | 모니터링 보안 그룹·규칙 | 전용 그룹과 규칙 8개를 현재 통신 관계 변경 없이 편입 |
| 1 | 나머지 EC2·루트 디스크 | AMI·키·유형·볼륨 속성 일치, 디스크 중복 소유 방지 |
| 2 | 전용 보안 그룹·규칙·EIP 연결 | 현재 통신 관계 유지, inline 규칙과 별도 규칙 리소스 혼용 방지 |
| 3 | IAM 역할·프로파일·정책 연결 | 관리형 정책 소유 범위 구분, 다른 작업의 권한 회수 방지 |
| 4 | S3·ECR | 삭제 방지, 기존 수명 주기·암호화·정책·태그 보존 |
| 5 | Glue 및 추가 발견 자원 | 파이프라인 생성 자원과 Terraform 관리 자원 충돌 방지 |

종속 자원을 아직 편입하지 않았다면 기존 ID/이름 참조로 먼저 연결. 해당 자원 편입 후 같은 값이 유지되는 리소스 참조로 전환.

각 묶음마다 `N to import, 0 to add, 0 to change, 0 to destroy`를 충족한 뒤 편입. 차이가 있으면 원인을 설명·해소한 뒤 다음 단계 진행.

모니터링 보안 그룹 1개와 규칙 8개는 PR #2 머지 후 사용자가 적용 완료. 원격 state의 관리 주소 등록을 읽기 전용으로 확인했고, 사용자 실행 후속 plan에서 `No changes` 확인. 다음 편입 대상은 모니터링 IAM 역할·인스턴스 프로파일·정책 연결.

모니터링 IAM 역할·인스턴스 프로파일·인라인 정책·관리형 정책 연결 5개는 PR #4 머지 후 사용자가 적용 완료. 원격 state의 관리 주소 등록을 읽기 전용으로 확인했고, 사용자 실행 후속 plan에서 `No changes` 확인. 최소 권한 조정은 사용 근거를 확보한 별도 변경으로 분리.

모니터링 S3 버킷 본체와 암호화·공개 접근 차단·소유권 설정 4개는 PR #6 머지 후 사용자가 적용 완료. 원격 state의 관리 주소 등록을 읽기 전용으로 확인했고, 사용자 실행 후속 plan에서 `No changes` 확인. 버전 관리와 보존 정책은 별도 운영 변경으로 분리.

남은 EC2 중 프로젝트의 크롤링·데이터 파이프라인 조율 역할이 명확한 Airflow 서버를 다음 대상으로 선정. import 전 user data가 비어 있음을 확인하고 `1 import, 0 add/change/destroy` 계획과 예상 주소·ID 일치를 검증. 현재 중지 상태는 그대로 유지하며 보안 그룹·IAM은 후속 편입으로 분리.

Airflow EC2 적용 후 연결 그룹의 사용 범위를 조사해 전용 그룹 1개와 규칙 4개를 편입 대상으로 선정. 프로젝트 EC2 네 대가 공유하는 SSH 그룹은 제외. 전체 프로토콜 규칙의 포트 정규화 차이를 해소한 뒤 `5 import, 0 add/change/destroy` 계획 확인. 외부 접근 범위 개선은 현재 상태 편입 후 별도 변경으로 분리.

Airflow 전용 보안 그룹 1개와 규칙 4개는 PR #11 머지 후 사용자가 적용 완료. 원격 state에서 관리 주소 5개 등록을 확인했고 후속 plan은 `No changes`. 다음 편입 대상은 Airflow IAM 역할·인스턴스 프로파일·정책 연결.

Airflow IAM은 역할과 인스턴스 프로파일이 1:1로 연결되고 해당 프로파일을 사용하는 EC2가 Airflow 서버 한 대뿐임을 확인. 역할 1개, 프로파일 1개, AWS 관리형 정책 연결 5개를 대상으로 `7 import, 0 add/change/destroy` 계획과 기존 관리 자원 무변경을 검증. 현재 권한 축소는 실제 DAG 사용 근거를 확보한 별도 운영 변경으로 분리.

Airflow IAM 자원 7개는 PR #13 머지 후 사용자가 적용 완료. 원격 state에서 역할·프로파일·정책 연결의 관리 주소 등록을 확인했고 후속 plan은 `No changes`. 다음 후보인 파이프라인 테스트 EC2는 현재 사용 여부와 장기 관리 가치를 먼저 확인한 뒤 편입 여부 결정.

파이프라인 테스트 EC2는 로컬 컴퓨터를 계속 켜두기 어려운 장시간 논문 크롤링을 위해 만든 임시 실행 서버로 확인. 현재는 장기간 중지 상태이고 재사용 여부가 확정되지 않았으며 전용 IAM 연결도 없음. 기존 서버 편입을 보류하고, 반복 사용이 필요해지면 Terraform으로 재생성 가능한 실행 환경과 외부 결과 저장 구조를 우선 설계. 현재 서버 내부의 보존 데이터를 확인하기 전에는 정리하지 않음.

## 5. 운영 변경과 복구 검증

- 태그 정리·접근 제한·백업 강화는 최초 편입과 분리한 변경 계획으로 진행
- PR마다 fmt·validate·plan 수행, 실제 apply 주체와 적용 이력 기록
- 주기적 plan으로 콘솔 변경 등 코드와 실제 자원의 차이 탐지
- 테스트 환경에서 EC2 재구성 → 기존 배포 도구 실행 → 데이터 복원 → 서비스 확인까지 연습
- 인프라 재구성 시간과 데이터 복원 시간을 나누어 측정

**포트폴리오에 남길 근거:** 이전 수동 절차, 인벤토리, 설계 선택, 변경 없는 import 계획, 변경 검토 사례, 장애 복구 실험 결과.

## 복구·중단 판단

- import 전 차이가 발견되면 apply 없이 코드 수정. 이때 AWS 자원에는 변화 없음
- 잘못된 주소에 편입했다면 잠금 확보와 state 백업 후 주소 이동·소유 관계 수정 검토
- state만 되돌려도 실제 AWS 변경이나 데이터 손실은 복구되지 않음
- 데이터 자원 교체가 필요한 변경은 별도 백업·복원 검증과 작업 계획 필요
