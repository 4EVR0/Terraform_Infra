# 논문 크롤링 EC2 안전 폐기

## 배경

- 로컬 컴퓨터 대신 장시간 논문 크롤링을 실행하기 위해 만든 임시 서버
- 크롤링 완료 후 장기간 중지됐고 상시 서비스나 자동화된 배치 실행에 사용되지 않음
- 전용 IAM·데이터 볼륨·재현 가능한 배포 절차가 없어 기존 서버를 장기 운영 자원으로 편입할 가치가 낮음

기존 EC2를 Terraform에 편입하는 대신 복구 지점을 만든 뒤 폐기하고, 필요 시 재생성 가능한 배치 환경으로 다시 설계하기로 결정.

## 백업과 폐기 결과

1. 종료 전 서버가 중지 상태이고 종료 방지가 비활성화된 상태 확인
2. 실행 구성과 루트 디스크를 포함한 비공개 AMI 생성
3. AMI `available`, 연결된 스냅샷 `completed 100%` 확인
4. 파이프라인 EC2 종료 완료
5. `DeleteOnTermination`으로 설정된 기존 루트 볼륨 삭제 확인
6. 복구용 AMI와 스냅샷은 별도 보존

AMI는 생성 완료 상태까지 확인했지만 실제 복원 인스턴스 부팅 시험은 수행하지 않음. 보존 기한을 정한 뒤 복원 필요성이 사라지면 AMI 등록 해제와 스냅샷 삭제 필요.

## 공용 SSH 자원 정리 계획

- GraphDB·Airflow·모니터링은 이미 검증된 대체 관리 경로로 전환 완료
- 파이프라인 EC2 종료 후 공용 SSH 보안 그룹을 사용하는 네트워크 인터페이스가 없음을 확인
- 공용 그룹 본체, 공개 TCP 22 인바운드 규칙, 전체 아웃바운드 규칙을 Terraform 구성에서 제거
- 정확히 검토한 세 자원만 삭제하는 plan 검사기와 회귀 테스트 추가

계획 결과: **0 to add, 0 to change, 3 to destroy**.

## 적용 게이트

1. PR 병합 후 `main`에서 새 plan 생성
2. 원격 state 백업
3. 공용 SSH 보안 그룹의 연결 대상이 여전히 0개인지 재확인
4. 계획 검사기로 삭제 대상 세 개 외 다른 변경이 없는지 확인
5. 사용자 apply
6. 실제 보안 그룹과 규칙 삭제 확인
7. 후속 plan의 `No changes` 확인

다른 네트워크 인터페이스 연결이 발견되거나 계획에 다른 자원 변경이 포함되면 적용 중단.

## 향후 크롤링 실행 구조

- Terraform으로 필요할 때만 실행 환경 생성
- 버전이 고정된 컨테이너로 크롤러 배포
- 결과와 체크포인트를 S3 같은 영구 저장소에 기록
- 작업 완료 후 컴퓨팅 자원 자동 중지 또는 제거

서버 내부 상태와 결과 데이터의 수명 주기를 분리해 동일한 작업을 다시 실행하고 복구할 수 있는 구조 권장.
