# Terraform 상태 복구 검증

## 목적

- S3 버전 관리에 남은 과거 Terraform 상태를 실제로 복원할 수 있는지 확인
- 복원된 상태를 Terraform이 정상적으로 읽고 현재 구성과의 차이를 계산하는지 확인
- 운영 상태를 건드리지 않는 격리된 시험으로 복구 절차와 한계 정리

Terraform 상태는 코드의 선언과 실제 인프라를 연결하는 기록이다. 상태를 이전 버전으로 되돌리는 일은 EC2나 데이터 자체를 복구하는 작업이 아니라, Terraform이 알고 있는 관리 관계를 이전 시점으로 되돌리는 작업이다. 따라서 복구 직후 계획을 검토하지 않고 적용하면 실제 인프라를 과거 상태에 맞추려는 변경이 발생할 수 있다.

## 시험 모델

실제 AWS 자원을 만들지 않는 내장 `terraform_data` 리소스 한 개를 사용했다.

| 구분 | 상태에 저장한 값 | 역할 |
|---|---|---|
| 상태 A | `first` | 마지막으로 확인된 정상 상태 |
| 상태 B | `second` | 문제가 생겼다고 가정한 최신 상태 |
| 복원된 A | `first` | S3 과거 버전을 새 최신 버전으로 등록한 상태 |
| 재복원된 B | `second` | 시험 전 최신 상태로 원상 복귀한 상태 |

상태 B는 실제로 깨진 JSON이 아니다. 정상적인 Terraform 상태이지만, 잘못된 import나 의도하지 않은 상태 변경이 발생한 상황을 단순한 값 차이로 재현했다. 손상된 JSON 자체의 파싱 실패를 확인하는 시험과는 목적이 다르다.

## 안전장치

- bootstrap 및 project 운영 상태와 다른 고유한 S3 key 사용
- key에 `verification/state-recovery/` 전용 경로 사용
- AWS provider 자원 대신 Terraform 내장 `terraform_data`만 사용
- S3 버전 관리 활성화가 확인된 기존 상태 버킷 사용
- 상태 파일과 VersionId 기록은 Git 제외 디렉터리에 저장하고 파일 권한 제한
- 이전 버전을 삭제하거나 기존 버전을 덮어쓰지 않고, 과거 내용을 새 최신 버전으로 업로드
- 복원 후 생성된 변경 계획은 적용하지 않고 검증 증거로만 보관

## 수행 절차와 각 단계의 의미

### 1. 상태 A 생성

- `probe_value = "first"`로 계획 생성 및 적용
- 같은 입력으로 다시 계획하여 `No changes` 확인
- 현재 S3 객체의 VersionId를 상태 A 식별자로 기록

이 단계는 복구 기준점인 마지막 정상 상태를 만드는 과정이다.

### 2. 상태 B 생성

- 입력을 `probe_value = "second"`로 변경
- 계획에서 `0 to add, 1 to change, 0 to destroy` 확인 후 적용
- 같은 입력으로 다시 계획하여 `No changes` 확인
- 상태 B의 VersionId를 별도로 기록하고 A와 다른 버전인지 확인

이 단계는 정상 상태 이후 새로운 상태가 저장된 상황을 재현한다.

### 3. 과거 상태 A 복원

- 상태 A의 VersionId를 지정해 로컬 파일로 다운로드
- JSON 형식, `lineage`, `serial`, 시험 값 `first` 확인
- 다운로드한 A를 동일한 S3 key에 다시 업로드하여 새 최신 버전 생성

S3 객체 버전 관리에서는 과거 버전을 삭제 없이 읽을 수 있다. 복원은 선택한 과거 내용을 다시 업로드하여 이를 최신 상태로 만드는 방식으로 수행했다.

### 4. 복원 상태 인식 확인

- 구성 입력은 계속 `second`로 유지
- Terraform 계획 실행
- 상태의 `first`와 구성의 `second` 차이에 대해 `0 to add, 1 to change, 0 to destroy` 확인

이 결과는 Terraform이 복원된 상태 A를 정상적으로 읽고 계획 계산에 사용했다는 근거다. 이 계획을 적용하면 상태가 다시 B와 같은 값으로 바뀌므로 적용하지 않았다.

### 5. 시험 전 상태 B 재복원

- 저장해 둔 상태 B 버전을 다운로드
- A와 B의 `lineage`가 같고 B의 `serial`이 더 크며 값이 `second`인지 확인
- B를 동일한 S3 key에 새 최신 버전으로 업로드
- `probe_value = "second"`로 최종 계획을 실행해 `No changes` 확인

이 단계로 시험용 상태를 시작 전 최신 상태로 되돌리고 검증을 종료했다.

## 검증 결과

- 상태 A와 B의 S3 VersionId가 서로 다름 확인
- 두 상태의 `lineage` 일치 확인
- 상태 serial이 A의 1에서 B의 2로 증가한 사실 확인
- A 복원 후 계획에서 `first`에서 `second`로의 변경 1건 탐지
- B 재복원 후 사용자 실행 결과 `No changes` 확인
- 운영 bootstrap/project 상태 및 실제 AWS 인프라 변경 없음

## 실제 장애에서의 적용 순서

1. Terraform 실행 주체를 모두 멈추고 진행 중인 정상 작업이 없는지 확인
2. 현재 상태를 별도 위치에 백업하고 S3 VersionId 기록
3. 장애 시각과 변경 이력을 기준으로 복구할 과거 버전 선정
4. 선택한 상태의 JSON 구조, `lineage`, `serial`과 대상 workspace 확인
5. 과거 상태를 같은 key의 새 최신 버전으로 복원
6. `terraform plan`으로 실제 인프라와 복원 상태의 차이 검토
7. 예상하지 않은 생성·변경·삭제가 있으면 적용하지 않고 원래 상태 복구 또는 원인 조사
8. 계획과 실제 인프라가 일치할 때만 복구 완료 처리

## 한계와 보완점

- 상태 복구는 삭제된 EC2, 데이터베이스 내용, S3 데이터 등 실제 자원을 되살리지 않음
- 실제 자원 복구에는 EBS 스냅샷, 데이터베이스 백업, 객체 버전 관리 등 자원별 백업 필요
- 이번 시험은 단일 리소스와 동일 lineage 안의 두 정상 상태를 사용
- 동시에 여러 사용자가 Terraform을 실행하는 상황과 잠금 해제는 이전 잠금 시험에서 별도 확인
- 팀 로그인과 최소 권한 정책이 확정되면 다른 사용자 계정으로 상태 읽기·잠금·계획 실행 검증 필요
